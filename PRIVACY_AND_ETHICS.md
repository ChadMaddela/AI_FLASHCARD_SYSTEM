# Privacy, Data Handling, and Ethical Use of AI

This document describes what learner and instructor data the AI-Driven
Adaptive Flash Learning System collects, how it is used, where it lives, and
the ethical considerations around its use of generative AI (Google Gemini) to
produce instructional content. It is written to support the accompanying
study, *"Development and Validation of AI-Driven Adaptive Flash Learning
System for Teaching Anatomy and Physiology"* (Reyes), and specifically to
give reviewers, instructors, and IRB/ethics evaluators a concrete account of
the system's data practices during the instructor-usage and pretest/posttest
phases of that research.

This is a policy and disclosure document, not a certification of legal
compliance. Sections below flag where a formal compliance review (e.g.
against the Philippine Data Privacy Act of 2012, RA 10173, or an
institution's own IRB requirements) would be a prerequisite to using this
system with real student data outside a research context.

## 1. What Data the System Collects

| Category | Fields | Collected From | Purpose |
|---|---|---|---|
| Account data | username, email (optional), hashed password, role (Student/Teacher) | Self-registration (`/register`) or teacher-driven promotion | Authentication, role-based access |
| Uploaded materials | Title, extracted text content, original file (PDF/DOCX/PPTX/image) | Teacher upload | Source text for AI flashcard generation; original file kept for reference |
| Flashcards | Question/answer or MCQ content, sub-topic tag | Generated by Gemini from uploaded material, or manually authored by a teacher | The actual learning content |
| Learning performance | Attempts, correct/incorrect counts, mastery level, SM-2 scheduling fields (ease factor, interval, due date) | Every student answer submission | Powers spaced repetition and analytics |
| Confidence ratings | Self-rated confidence (Guessing/Unsure/Confident) + whether that attempt was correct | Student, before seeing feedback on a card | Metacognitive calibration analytics |

Passwords are never stored in plain text (Django's `set_password`/PBKDF2
hashing). No payment information, precise location, or device/browser
fingerprinting data is collected anywhere in the system.

## 2. How Google Gemini Is Used

- **What is sent**: only the *extracted text of a teacher-uploaded material*
  (e.g. a lecture's text content) plus a fixed instructional prompt asking
  for MCQ or front/back flashcards. No student names, performance data,
  confidence ratings, or account credentials are ever included in a Gemini
  request — the generation task (`core/tasks.py`) only ever receives
  `material.content_text` and a card-type flag.
- **What comes back**: structured JSON (question/answer or question/choices)
  that becomes `Flashcard` rows. Nothing from Gemini's response is executed
  as code or trusted as ground truth automatically — see §5 below.
- **Storage of AI output**: generated flashcards are stored the same way as
  manually authored ones, and a teacher can edit or delete any AI-generated
  card via the flashcard management page.

## 3. Where Data Lives

- **Structured data** (accounts, materials, flashcards, performance,
  confidence ratings): a managed Postgres database (Supabase).
- **Uploaded files**: Supabase Storage, linked from the `Material` record via
  a public URL; deleting a material also attempts to remove the
  corresponding stored file.
- **Background task queue** (Redis/Celery): holds only transient task
  messages (a material ID and a generation-mode flag) while a flashcard
  generation job is in flight — no learner performance data passes through
  Redis.
- **Client-side**: the JWT access token and a display name/role are kept in
  `localStorage` in the browser for session continuity; no analytics or
  performance data is cached client-side beyond the current page's state.

## 4. Data Retention & Deletion — Current State and Limitations

**This is deliberately reported as-is, not idealized:**

- There is currently **no automated retention policy** (e.g. auto-purging
  old performance data) and **no self-service "export/delete my data"
  feature** for students. A teacher can delete a `Material`, which cascades
  to delete its `Flashcard` rows and, in turn, any `StudentPerformance` and
  `ConfidenceRating` rows tied to those cards — but there is no path for a
  student to independently request deletion of their own account or
  learning history today.
- This is flagged explicitly as a **gap to close before any deployment
  involving real students outside a supervised research context** — see the
  Recommendations section below and the companion `SUSTAINABILITY.md` for
  how this could be phased in.

## 5. Ethical Use of AI in Instruction

Anatomy and Physiology is a domain where **factual accuracy has real
consequences** — an LLM can produce plausible-sounding but incorrect
statements about anatomical structures or physiological processes
("hallucination"). This shapes several design and process commitments:

1. **AI drafts, instructors approve.** Generated flashcards are treated as a
   *draft* that a subject-matter instructor should review before students
   rely on them for study. The system deliberately keeps full teacher
   edit/delete control over every generated card rather than hiding them
   behind an opaque "AI-verified" label.
2. **Transparency to students.** Students should be told, as a matter of
   course by the instructor, that flashcards may be AI-generated and
   instructor-reviewed, not authored from scratch by the instructor.
3. **No autonomous grading of open-ended clinical judgment.** The system
   only scores objective recall (MCQ correctness, self-graded recall
   ratings) — it does not attempt to auto-grade free-text clinical reasoning,
   which would carry much higher accuracy risk.
4. **Human-reported issues matter.** Anticipated instructor-reported
   challenges around AI-generated content quality (directly relevant to the
   study's second research question on challenges instructors face) should
   be logged and fed back into prompt or review-process improvements — see
   `SUSTAINABILITY.md` §4.

## 6. Relationship to the Study's Validation Criteria

The study evaluates the system across nine dimensions (Objectives, Content,
Activities, Language and style, Organization, Presentation, Evaluation,
Usefulness, Navigation). Data handling and AI-ethics choices most directly
touch:

- **Content** — accuracy of AI-generated material depends on the
  human-review step in §5; this is the system's primary content-quality
  safeguard and should be called out explicitly to expert evaluators.
- **Evaluation** — the mastery/analytics computations (`core/analytics.py`)
  are deterministic and auditable (SM-2 scheduling math, aggregate SQL), not
  themselves AI-driven, which keeps assessment scoring explainable.
- **Usefulness** — the confidence-calibration analytics (§1) give both
  students and instructors a direct, evidence-based signal of self-regulated
  learning, which is a concrete, checkable claim for expert reviewers rather
  than an abstract one.

## 7. Recommendations / Future Work

Explicitly **not implemented** in the current system, listed here so they're
visible as deliberate scope decisions rather than oversights:

- Student-facing consent capture at registration (a checkbox acknowledging
  data collection and AI-generated content).
- A self-service "export my data" / "delete my account" flow.
- A lightweight moderation/flagging queue for instructors to report
  incorrect AI-generated content, feeding into prompt refinement.
- A configurable data-retention window for inactive accounts.
- A formal legal/compliance review (RA 10173 or equivalent) before any use
  with real students outside a supervised research/validation context.
